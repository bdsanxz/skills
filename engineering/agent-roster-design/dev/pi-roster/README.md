# pi-roster

A local Pi extension for recurring and self-paced prompt loops.

## Install / use

Load with `pi --extension /absolute/path/to/index.ts`. The shippable extension is the built `scripts/pi-roster.js`: in `dev/pi-roster`, `bun run build` bundles `index.ts` and `logic.ts` into that one file (deterministic: same source, same bytes), which pi loads with `-e` like the source; the installed pi docs confirm plain `.js` files load. Check it with `bun run typecheck` and `bun run test`. Run `/loop 5m check deployment` for a recurring loop, or `/loop check deployment` for a dynamic loop (initial 20-minute wakeup). Every `/loop` with an interval or a new task creates its own loop (`loop-1`, `loop-2`, ...): two interval loops with different tasks or intervals run side by side. Repeating the same interval and task reports `Already running as <id>` instead of doubling. Dynamic loops are keyed by task text: a `Schedule` call with the same `prompt` replaces that loop's pending wakeup only, a different `prompt` is a different loop, and `Schedule` never touches interval loops. `Schedule { stop: true, prompt: "<text>" }` stops that dynamic loop only; `Schedule { stop: true }` without a prompt stops every dynamic loop. Interval mode runs immediately with the plain prompt, then uses only the extension timer. `Schedule` chooses a delay, reason and noop state for dynamic loops; another call with the same prompt replaces that loop's timer. Use `/loop list` (bare `/loop` works too) to print every loop with id, kind, interval or next fire time, shortened task, noop streak and pending state; `/loop stop <id>` stops one loop and `/loop stop` stops all of them. The status line shows the loop count and the earliest next fire. At most 10 loops run per session (`ROSTER_MAX_JOBS`, default 10).

## Tick coalescing

Each loop keeps its own pending flag, so the one-pending-tick rule is per loop: a tick is injected only when its loop has no pending prompt. Idle injects, busy with nothing pending injects and marks pending, and a tick that fires while its loop still has a pending prompt is dropped (`timer_skipped` carries that loop's id). Ticks from different loops never block each other except through the normal busy queue. The flag clears when pi starts handling that tick: `before_agent_start` covers a tick that starts a new run, while `message_start` (matched on the user message text) covers a queued `followUp` tick that runs inside the same agent loop without a new `before_agent_start`; both log `tick_consumed` with the loop id and the event used. Two safety valves back them up per loop: `agent_end` clears a still-pending flag when nothing is queued (`hasPendingMessages()` false), and a flag older than its max age clears on the next timer fire (logged as `tick_pending_expired` with the loop id), defaulting to 3x the loop interval with a 60 s floor, overridable via `ROSTER_PENDING_MAX_MS`. Interval loops still reschedule their next tick after a skip; a dynamic wakeup is one-shot, so a skip needs no reschedule (the pending iteration reschedules via `Schedule` when it runs).

## `/goal` session Stop hook

One session-scoped completion condition. `/goal <condition>` sets it (replacing any existing goal) and injects one hidden meta user turn so the agent starts work immediately; bare `/goal` shows the panel (`No goal set` or `Goal active` with elapsed time, turn count, token count, condition, and last check reason); `/goal clear` stops it early. At the end of every agent turn (`agent_end`), while a goal is active, a separate evaluator call receives the condition plus a compact transcript and returns `{met, reason}`; `met: false` shows `◯ Goal not yet met… continuing` and injects `Stop hook feedback:\n[<condition>]: <reason>` as a `followUp` user turn, `met: true` shows `✔ Goal achieved (…)` and clears the goal. Evaluation is skipped when queued messages are pending (background work will re-invoke the agent), and a stale verdict never injects after clear, replace, or shutdown (generation guard). Caps: `ROSTER_GOAL_MAX_CHECKS` (default 30) consecutive unmet checks stops the goal (`goal_cap_reached`); evaluator failure or timeout (`ROSTER_GOAL_EVAL_TIMEOUT_MS`, default 60000) counts as unknown, is retried at the next turn end, and clears the goal after 3 consecutive failures. The transcript sent to the evaluator is capped at `ROSTER_GOAL_TRANSCRIPT_MAX_CHARS` (default 12000, newest tail). One goal per session; it coexists with `/loop` (a loop tick is just another turn). New JSONL events: `goal_set`, `goal_cleared`, `goal_check` (met, reason, duration_ms), `goal_continue`, `goal_achieved`, `goal_skipped_background`, `goal_eval_failed`, `goal_cap_reached`. Only transcript lengths are logged, never transcript text.

## Extension API findings (pi 1.4.0, `@earendil-works/pi-coding-agent`)

- Register a command: `pi.registerCommand("goal", { description, handler: async (args, ctx) => {...} })`; the handler receives raw args plus an `ExtensionCommandContext`. Commands are listed via `pi.getCommands()`.
- Read the session transcript: `ctx.sessionManager.getBranch()` returns the active branch entries (the pattern used by the `qna` and `summarize` examples); message entries carry `role`/`content` with string or text-block array content. The `ReadonlySessionManager` type also exposes `getEntries()`, `buildContextEntries()`, and `buildSessionProjection()`.
- Separate model call that does not touch the session: `ctx.modelRegistry.complete(ctx.model, { systemPrompt, messages }, { signal })` runs a provider-neutral call with the session's current model and its configured credentials (used by the `summarize` example with `find`/`hasConfiguredAuth`/`complete`, and by `qna` with `streamSimple` plus a UI loader and abort signal). The result never enters the transcript; only its `usage.totalTokens` is folded into goal totals.
- Inject a user turn after `agent_end`: `pi.sendUserMessage(text, { deliverAs: "followUp" })` always triggers a turn and queues behind running work; `agent_end` fires per low-level run (queued `followUp` drains inside the same run, so a `/goal clear`, a new `/goal`, or shutdown is guarded by a generation counter so no stale evaluation injects afterwards). The evaluator runs from `agent_end` only when `ctx.hasPendingMessages()` is false; `agent_before_settle` (one final continuation) and `agent_settled` (notification-only, after all automatic continuation) were deliberately not used because the goal must re-check after every turn, not once at settlement.
- Status line and widget: `ctx.ui.setStatus("goal", "◎ /goal active (<elapsed>)")` shows footer text (cleared with `undefined`), `ctx.ui.setWorkingMessage("running Stop hook")` shows the evaluator call (restored with no argument), and `ctx.ui.notify(text, "info" | "error")` surfaces goal transitions. `ctx.ui.setWidget()` and `setFooter()` exist but were not needed.

## Limits and logging

Cron create/list/delete tools are out of scope. Timers are process/session-local and every loop's clock timer is cancelled on session shutdown. `/loop stop <id>` clears that loop's timer and pending flag, `/loop stop` clears all of them, and each removal logs its own `cancel_stop` with the loop id. Already-queued `followUp` prompts cannot be retracted: the public extension API exposes `hasPendingMessages()` (read-only) and `abort()` (aborts streaming, not the queue), while `clearQueue()` exists only on the internal session class and is not exposed to extensions. Queued ticks therefore still run once each after a stop, but no new ticks stack. Duplicates reuse the existing id and log `schedule_duplicate`; creating past the cap returns a clear error and logs `schedule_cap_reached`. JSONL events are appended to `logs/roster.jsonl` with `ROSTER_LOG` set to that path; otherwise the default is `~/.pi/agent/logs/roster.jsonl`. Events include extension load, raw/parsed commands, first iteration, timer schedule/fire/skip (`timer_skipped` with reason `previous_prompt_pending`), message injection and busy state, tick consumption, Schedule params/clamped delay/noop streak, cancellation/stop, session shutdown, and caught errors with stack. Logging failures are ignored. Busy-session queue semantics depend on Pi's `followUp` delivery.
