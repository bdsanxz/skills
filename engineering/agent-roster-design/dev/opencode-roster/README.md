# opencode-roster

OpenCode v2 roster extension: default-export plugin plus a local stdio MCP sidecar.

## Install

The v2-format plugin entrypoint is `.opencode/plugins/opencode-roster.ts` and uses a default `{ id, setup }` export. It registers the `loop` command and embedded `loop` skill through `context.command.transform` and `context.skill.transform`. The shippable sidecar and plugin are the built `scripts/opencode-roster-mcp.js` and `scripts/opencode-roster-plugin.js`: in `dev/opencode-roster`, `bun run build` bundles `src/mcp/server.ts` (with its imports) and `.opencode/plugins/opencode-roster.ts` into those files (deterministic: same source, same bytes). Check them with `bun run typecheck` and `bun test`.

```json
{
  "mcp": {
    "servers": {
      "roster": {
        "type": "local",
        "command": ["bun", "run", "/ABS/PATH/scripts/opencode-roster-mcp.js"],
        "environment": { "ROSTER_LOG": "{env:ROSTER_LOG}" },
        "codemode": false
      }
    }
  }
}
```

The sidecar finds the OpenCode service itself: explicit `OPENCODE_URL` / `OPENCODE_SERVER_PASSWORD` (or `OPENCODE_SERVER_URL` / `OPENCODE_PASSWORD`) first, then read-only `opencode service status` / `opencode service get password`, then the service state and config files. It logs `service_discovered` with the source of each value and `service_unresolved` with the exact commands it tried when a value is missing.

OpenCode v2 MCP supplies the session ID as `params._meta["ai.opencode/sessionID"]`; this is request metadata, not an argument, and can be missing. The server returns an explicit error if absent. Start `opencode serve --port 4097` (or another fixed port) and set `OPENCODE_URL` to its base URL. Auth accepts `OPENCODE_SERVER_PASSWORD` or `OPENCODE_PASSWORD`; Basic auth user is `opencode`, and the password is never logged. OpenAPI v2.0.29 confirms `POST /api/session/{sessionID}/prompt` (operation `session.prompt`) expects `{text, delivery, resume}`; this may block until the turn ends, so the sidecar fires the fetch without awaiting it and logs failures. `GET /api/event` (operation `event.subscribe`) is SSE; the sidecar observes `session.execution.started` (busy) and `session.execution.succeeded` / `failed` / `aborted` / `cancelled` (idle), plus `session.step.started` (busy), to maintain its busy queue. MCP session metadata is used to target the original same session. Run `bun install`, `bun test`, and `bun run typecheck` for local checks.

JSONL instrumentation is written by plugin and MCP sidecar to `logs/roster.jsonl`; set `ROSTER_LOG` to override it. The `logs/` directory is ignored by git. Events include `plugin_loaded`, `command_registered`, `skill_registered`, `mcp_starting` (with sidecar pid), `mcp_call`, `command_received`, `first_iteration_sent`, `timer_scheduled`, `timer_fired`, `message_injected`, `tool_call`, `tool_result`, `event_type_seen`, `busy_released` (reason names the SSE type, e.g. `session_execution_succeeded`), `cancel_stop`, `sse_reconnect`, and `error` (with stack where available). Lines contain ISO `ts`, `event`, optional `session_id`, and `details`. Logging is best-effort and never throws.

## Use

- MCP tools appear as native `roster_Schedule`, `roster_ScheduleCreate`, `roster_ScheduleList`, and `roster_ScheduleDelete` because `codemode:false`.
- A session may run up to 10 loops at once (`ROSTER_MAX_JOBS`, default 10). Each loop has an id (interval loops keep their cron ids) and a kind (`interval` or `dynamic`). `/loop list` (also bare `/loop`) lists every loop via `roster_ScheduleList`: id, kind, interval or next fire time, task (shortened to 80 chars), noop streak, pending state; the list length is the loop count and the earliest due is the next fire. `/loop stop` ends ALL loops via `roster_Schedule` with `stop:true`; `/loop stop <id>` ends one loop via `roster_ScheduleDelete({id})`, or for a dynamic loop via `roster_Schedule` with `stop:true` and that loop's exact prompt text (which stops that loop only). Dynamic wakeups are keyed by prompt text: scheduling the SAME prompt replaces that loop's wakeup only, a different prompt is a different loop.

1. Replace `/ABS/PATH/opencode-roster` above with this directory's absolute path. Save the MCP object under `mcp.servers.roster` in this project's `opencode.json`; keep `codemode:false` and the MCP command's cwd as the project path.
2. In one terminal start `OPENCODE_SERVER_PASSWORD='choose-a-local-password' opencode serve --port 4097`. In another, set `OPENCODE_URL=http://127.0.0.1:4097` and `OPENCODE_SERVER_PASSWORD` to the same password (MCP config environment entries above), then start the TUI from this project with `opencode --standalone --print-logs --log-level debug .` (or `opencode --standalone .` if you prefer interactive approvals). Run `/mcps` and confirm `roster` is connected. Verify `logs/roster.jsonl` includes `plugin_loaded`, `command_registered`, `skill_registered`, and `mcp_starting`.
3. Enter `/loop 5s say tick`; confirm “tick” runs immediately and then at least twice more, about 5 seconds apart (intervals accept 1s through 1h). The model must make exactly one `roster_ScheduleCreate` call with interval `5s` and prompt `say tick` (the task only, without the leading `/loop` and interval; e.g. `/loop 5s run sleep 12 seconds` -> `{interval:"5s", prompt:"run sleep 12 seconds"}`), and nothing else (no `Schedule`, `ScheduleList`, or `ScheduleDelete`). A repeated `roster_ScheduleCreate` with the same session, interval and prompt returns the existing id (`already scheduled (already running as <id>)`, logged as `schedule_duplicate`) instead of a second job. Two interval loops with different tasks or intervals run side by side with separate IDs. Inspect the log for `command_received`, `first_iteration_sent`, `timer_scheduled`, `timer_fired`, and `message_injected`; a `ScheduleCreate` prompt carrying `/loop` is stripped defensively and logged as `prompt_normalized`.
4. Enter `/loop check the build`; confirm one immediate iteration. Ask the model to use `roster_Schedule` with the exact prompt `/loop check the build`, delay 5 (clamped to 1–3600), a short reason, and noop false; verify the next prompt arrives in the same session. Schedule a second dynamic wakeup with a different prompt (e.g. `/loop watch the queue`) and confirm both wakeups coexist; rescheduling the first prompt replaces only that loop's wakeup. Call `roster_Schedule` with `stop:true` and `prompt:"/loop check the build"` and confirm only that loop stops; call with `stop:true` alone and confirm every remaining dynamic loop (and any cron job) stops.
5. Start a long-running task and separately schedule a 5-second wakeup; let the session remain busy at fire time. Confirm log `message_injected` has `busy:true, queued:true`, then the queued message is delivered once right after the SSE `session.execution.succeeded` frame (`busy_released` with reason `session_execution_succeeded`), without waiting for the 1 s safety probe. If a job fires while its previous prompt is still queued, confirm `timer_skipped` carries that loop's id (`job_key`/`loop_id`) and the new tick is dropped; ticks of different loops queue and deliver independently.
6. Call `roster_Schedule` with `stop:true`; verify no next firing from any dynamic wakeup or cron job, and one `cancel_stop` per cancelled job plus a summary line. Call `roster_ScheduleList` and confirm it lists every loop with id, kind (`interval`/`dynamic`), interval or next fire time, task (shortened), noop streak, and pending state; the list length is the loop count and the earliest due is the next fire. Enter `/loop list` (also bare `/loop`) and confirm the same listing; enter `/loop stop <id>` (via `roster_ScheduleDelete({id})`) and confirm only that loop stops.
7. Call `roster_ScheduleCreate` twice with different prompts/intervals; call `roster_ScheduleList` and confirm separate IDs with `kind:"interval"`; delete one with `roster_ScheduleDelete({id})` and verify the other remains scheduled. Call `roster_ScheduleCreate` again with the same session, interval and prompt as an existing job and confirm it returns the existing id (`already scheduled (already running as <id>)`, logged as `schedule_duplicate`) without a second job. Creating more than `ROSTER_MAX_JOBS` loops per session (default 10, counting dynamic and interval loops together) returns an error (logged as `schedule_cap_reached`). Never delete the loop's own running job; only `/loop stop` ends every loop.
8. Confirm each `event_type_seen` type appears exactly once. If a type repeats, a stale sidecar is still running (the sidecar now exits when OpenCode drops its stdio pipes and logs its pid in `mcp_starting`); kill leftover `bun run src/mcp/server.ts` processes. Confirm `sse_reconnect` delays double (500 ms, 1 s, 2 s, …) up to 30 s after failures instead of sticking at 500 ms.

## Limits

Timers are in-memory in the MCP sidecar and are lost if it exits. `Schedule` keeps one active timer per prompt (dynamic loops keyed by prompt text; the same prompt replaces only that loop's wakeup), while cron jobs are independent IDs; every loop has one pending prompt (per-loop pending flag, safety valves, and `timer_skipped` carry the loop id) and ticks of different loops never block each other except through the normal busy queue. At most 10 loops per session (`ROSTER_MAX_JOBS`, default 10); beyond it calls fail with `schedule_cap_reached`. The plugin API registers only the prompt template and skill; MCP supplies tools. Sidecar session URL uses `OPENCODE_URL` or defaults to localhost:4096. Prompt injection is fire-and-forget over `session.prompt` with queue delivery enabled; it does not wait for the model turn to finish. The sidecar watches live v2 `{id, created, type, data, location?, durable?}` SSE frames (legacy `{id, type, properties}` tolerated): `session.execution.started` and `session.step.started` mean busy, `session.execution.succeeded` / `failed` / `aborted` / `cancelled` mean idle, with the session id taken from `data.sessionID`. It logs each distinct frame type once as `event_type_seen`, and releases busy as `busy_released` on SSE idle, reconnect, probe, error, or a 120 s max-busy timeout (`ROSTER_BUSY_MAX_MS`). If event streaming fails it reconnects with doubling backoff (500 ms to 30 s), resetting only after frames arrive. The sidecar keeps a single SSE consumer per process and exits when its stdio pipes close. There is no persistent status panel or durable schedule storage.
