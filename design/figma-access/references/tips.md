# Tips

Lessons from real runs of this skill. They are not rules: each says what tends to go wrong in a situation and what usually works. Use judgment when your case differs. Read the section for the situation you are in.

## Reading the output

- Each top-level KDL node is one field of the result, encoded as JSON-in-KDL, so the file holds exactly what the API returned: an object's plain fields are `key=value` properties on its line, nested objects and arrays are indented blocks under it, array items are nodes named `-`, `(array)` marks a list, and `#true`, `#false`, `#null` are the literals. Check `ok #false` and `error` first.
- Search saved files line by line: a Figma node and its plain fields share one line, so `grep -n 'id="1:8614"' file.kdl` finds a node, `grep -c 'type=TEXT'` counts text layers, and `grep -n 'fontFamily="Inter"'` finds where a font is used (the `style` line under each text node). The line number and indentation show where the hit sits in the tree. Nested values (fills, effects, boxes) are on their own lines below the node, so for "nodes whose fill is X" read the block around the hit, or use `spec`.
- For processing that needs the whole tree, pass the file to `spec --from`, which reads `.kdl` and `.json`, or parse it with a KDL v2 library and decode each top-level node with its JSON-in-KDL support. Inputs the CLI takes from you (`call` params, `-p` files) stay JSON.

## Choosing a path

- **A Figma URL and a read-only job** (inspect, implement in code, export, audit) usually means REST: it needs nothing from the user and works when Figma Desktop is closed. Check with `figma-access status` whether a plugin is connected before asking the user to open one.
- **Changing the design** always needs the plugin. Use REST only to read around it.
- **Both available:** REST gives the saved file; the plugin sees what is on screen now. When they disagree, the user has unsaved or newer edits; trust the plugin.

## Token

- The token is read from `FIGMA_TOKEN_KEY`, `FIGMA_ACCESS_TOKEN` or `FIGMA_TOKEN`. Users often export it in a shell profile (`~/.zshrc`, `~/.bashrc`) that an agent's shell does not load, so the command says no token is set although the user set one. Load the profile in the same command: `source ~/.zshrc >/dev/null 2>&1; figma-access ...`. Look for the variable name in the profiles with `grep -l` rather than asking the user again.
- `figma-access api /v1/me` answers 200 for a working token; 403 means invalid, expired, or without access to the file.

## Finding the right node

- **`node-id` in a URL is often the page,** not the design: `node-id=0-1` is the first page. `figma-access node <url>` on a page says so and lists its frames; pick the frame the user means (usually the one top-level frame, or the one whose name matches the request) and work on its id.
- URL ids use `-` (`1-8543`); the API uses `:` (`1:8543`). The CLI converts both ways.
- Ids that start with `I` and contain `;` (`I1:8544;1038:92027`) are layers inside a component instance. They are valid for `render` and `node` (quoted), but in the plugin they change when the instance is swapped or reset.
- **Read the outline first** (`file`, or `node --outline 2`), then fetch details only for the part you work on. A whole landing page is megabytes of node data; reading it all wastes your context.
- **For code, read `spec`, not the node file.** `spec` prints one CSS-ready line per visible node (a 3 MB landing page became about 600 lines). Run it once on the whole frame, write it to a file with `-o`, and `grep` that file per section. On a long page whose spec is too much to read at once, write one spec per section instead (`spec <key> <section id> --from <node file>`, boxes relative to the section) and finish each section before reading the next.

## Rate limits and the cache

- The REST API answers 429 ("Rate limit exceeded") after a handful of large reads in a row. The CLI waits and retries on its own (up to two minutes) and caches every `file` and `node` read under `~/.figma-access/cache`, so repeating a command costs nothing. Pass `--refresh` only after the design changed.
- Fetch a big frame once with `node <key> <frameId> -o <file>` and give that `.kdl` file to every later `spec` run with `--from <file>`: `spec` then reads any node inside it without calling the API.
- Batch renders: `render <key> id1 id2 id3 ...` is one request for all ids. Rendering icons one call at a time is what usually runs into the limit.

## Hidden layers

- Design files keep a lot hidden: old versions, alternative states, "graveyard" copies, whole duplicated sections. In one real landing page 11,102 of 12,090 nodes were hidden, and some hidden frames sat exactly on top of visible ones (a second navbar, an old shop section).
- `node` removes hidden layers from the saved data by default and counts them in `prunedHiddenNodes`; the outline marks a hidden node with `hidden=#true`. Keep them (`--keep-hidden`) only when the user asks about alternative states.
- When the node data and the render disagree, look for a hidden layer, a mask, or a clip (`clipsContent`).

## Reading a design image

- An image larger than about 2000 px on a side is shown to you shrunk, and small text and 1 px lines vanish. `render` prints each PNG's size and notes when this applies. Cut a tall page into strips of about 1500 px with any image tool and read each strip.
- Render at scale 1 for a reference that matches CSS pixels one to one; scale 2 to read small text or icon detail.

## From design to code

- **`spec` already speaks CSS:** hex colors, flex direction, gap, padding, justify, align, sizing, radii, shadows, gradients. Where you read the node data yourself: positions are canvas coordinates (subtract the frame's corner, which `spec --origin` does for you), colors are 0..1 floats, and a shadow's `radius` is its blur.
- **Box, render bounds and export bounds differ.** `[x,y wxh]` in `spec` is the layout box. `render[...]` is what is visible on the canvas (clipped by parents). `export[...]` is the area a file from `render` covers: shadows and blurs grow it (a 40 px button with a 4 px shadow exports as 48 px, shifted 4 px left), masks shrink it to the mask, and clipping by parents is ignored (a decoration hanging 271 px off the frame exports whole). Place an exported file at its `export` position and size (its box when none is printed), inside a parent with `overflow: hidden` when the design clips it. The same holds for the frame you implement: its own shadow widens its render (a 1440 px frame rendered 1453 px wide), so compare against its box: `compare --nodes` crops the reference for you.
- **Stale boxes.** The API returns the boxes Figma last stored, and they can break the frame's own auto layout rules, usually because a hidden child is still counted or an edited text or instance was not laid out again. `spec` marks such frames `LAYOUT DRIFT (...)`; the stale box may be the frame's own or a child's (a menu item hugging 103 px was right, its child's stored 65 px was not; a button's fill layer was stored 326 px wide inside a 100 px button). Copying the boxes misplaces everything below them: one header stored 88 px tall for a 48 px title pushed every section 38 px down. Rebuild the auto layout rules in CSS with the real content and let the browser lay it out, since Figma's renderer applied the same rules; in one page this matched the render to the pixel where the boxes were 76 px off. Where a drifting part has no auto layout, measure its position on the render. A negative gap between page sections usually means the same: a stored height is too large.
- **Groups and frames without auto layout** place each child at its own box: `spec` prints no `flex` for them. Position their children absolutely inside a relative parent at the printed offsets, and size the parent to the group's box; flex applies again inside each child that has it.
- **Inside strokes take no space.** `border 1 inside` in `spec` is drawn over the box, and the frame's padding still counts from its outer edge. A CSS `border` takes space instead: it grows the box, or with `box-sizing: border-box` keeps the size but moves the content in by its width (every child of a bordered card 1 px off). Draw it with `box-shadow: inset 0 0 0 1px ...`, or subtract the border width from the padding.
- **Hug text is a little wider in Figma.** An auto-width text box is stored rounded up (`Product`: box 58 px, glyphs 55.6 px), while the browser sizes it to the exact advance. In a row aligned right or centred, the difference adds up across the items (5 px in one navigation bar). Where such a row must line up, give each text the box width from `spec`.
- **Fixed-height text boxes** may be taller than their lines; `valign center` or `valign bottom` in `spec` then places the lines (a 24 px line in a 30 px card title box sits 3 px lower). Add the padding, or use flex centring.
- **Repeated items** (cards, list rows, tabs) are usually instances of one component: compare their `componentId` to find which ones share code, and build one component with props. The copies are often not identical, though: instances get detached, resized or edited by hand (in one grid, cards of one component were 213.6, 228 and 229.6 px wide). For a 1:1 result give each copy the sizes `spec` prints for it, as props or modifiers; when the user wants clean code instead, make them uniform and say which copies you normalised.
- **Line breaks.** Designers break lines with Shift+Enter, which stores U+2028; `spec` prints it as `\n`. Keep those breaks (`<br>` or `white-space: pre-line`). Without a `\n` the text wraps by width, so do not add a `<br>` because the render shows a second line; if the wrap looks unlikely, measure the line (`canvas.measureText`) against the box width ("Langkah Mudah Daftar" was 167.8 px for a 166 px box).
- **Mixed-style text** shows its runs in `spec` (`runs[ "13": base | " GB ": ... | "| 30 Hari": font Poppins 400 16/24 ]`). Build each run as its own `<span>`.
- **Gradients:** copy them as `spec` prints them. It converts the handles with the node's size, including the third handle, which tilts the colour lines (a card overlay whose first two handles point straight down is drawn at 197deg, not 180deg); a hand-made angle from the raw handles came out visibly wrong. Fills are printed top layer first, as a CSS `background` lists them. Radial gradients are printed with the horizontal radius first, as CSS reads them; one marked `ROTATED <angle>deg` has a tilted ellipse that CSS cannot draw in a background, so take it out of the list and draw it on its own layer at the same place in the stack: an absolutely positioned child or pseudo-element centred on the gradient's centre, large enough to cover the element after turning, with that gradient and `transform: rotate(<angle>deg)`, inside a parent with `overflow: hidden`.
- **The frame is one screen size.** A desktop design is usually a 1440 px frame with a 1240 px content column. Copying `width: 1440px` onto the body and sections pins the page to the left of a wider window, with backgrounds ending at 1440 (a user caught this on a 1920 px screen). Centre the column with `margin: 0 auto` and keep the design's side padding as the smallest gutter. Something cut off at the frame edge (a carousel) needs a choice: clip it at the column or let it run to the window edge; say which.
- **Device and browser chrome are not the page.** Mockups often include a browser toolbar, status bar or device frame (for example an 80 px "Browser & URL Controls" instance at the top). Crop it off the reference too before comparing (`compare --crop`).
- **Fonts:** `node` lists every font family and text style, and the saved node data names each one's file (`fontPostScriptName`); check every weight, because a project often has the brand's Bold but not its Regular. Public families (Poppins, Inter, Roboto) can come from Google Fonts; brand fonts usually sit in the project or come from the user.
- **Pick a stand-in font by width, not by look.** Wider text wraps into extra lines and pushes everything below it. Try each candidate in the page and keep the family whose `widthRatio` in `compare --nodes` is closest to 1 for that style; for a quick first cut, measure the string with `canvas.measureText` against the `render[...]` width in `spec`. In one run Poppins 700 was 12 to 15% wider than the brand font and broke card titles into three lines; Outfit 700 was within 1%.
- **Images:** render the image nodes, or the frame that crops them, at `--scale 2` in one call: the file shows each image exactly as the design crops, scales and tints it, its own strokes included, so do not add that border again in CSS. Rebuilding the crop from the original rarely works: `spec` prints the scale mode (`image(<ref>, FILL)`), not the crop, and in one run a STRETCH photo rebuilt with `object-fit` left its card at 20% differing pixels. Reach for `image-fills` only when you need an original at full resolution with a plain FILL (`object-fit: cover`) or FIT (`contain`); it downloads every image in the file, hidden ones included.
- **Masks and illustrations:** a node marked `MASKED` or `ICON` renders right only as a whole: SVG for vectors, PNG at scale 2 for anything with photos or blurs.
- **Icons:** render them as SVG in one call (`--format svg`) rather than drawing them or cropping a PNG. Strip the fixed width and height if one must scale, and use `currentColor` when it is recoloured. The file covers the whole node, padding included (a flag frame with 4 px top padding exports 16×36 with the flag 4 px down), so do not apply that padding again. Rendered SVGs reuse ids such as `mask0_0_4590`; two inlined in one page can take each other's masks and gradients, so load them with `<img>` or rename the ids.
- **Compare by measuring, then by eye.** `compare --nodes` names the sections after the frame's children; to measure a smaller part, name it in `--sections` from the boxes in `spec` (`nav=0-48;cards=399,289,602,496`), and pass `--crop` when the reference holds chrome the page leaves out. Fix the section that differs most first. A threshold on differing pixels misses gradients and tints, so read the `mean` for those. When only text edges remain red in the difference image, the layout matches.
- **Separate position errors from content errors.** When `compare` reports a `shift` for a section, its content is right and something before it has the wrong height or width; find where the shift starts instead of editing the section.
- **Text sits a pixel off by style, not at random.** Browsers round a font's ascent and descent to whole pixels and Figma does not, so every text of one style (family, weight, size, line height) can land the same fraction of a pixel off while its box is right. `compare --nodes` measures it per text node and sums it up per style (in one page every Poppins 16/24 and 13/24 text sat 1.0 px high; 12/20 and 14/20 were within 0.1 px). When the offset is the same for every copy of a style, correct it once for that style, with a comment saying why; it took one navigation bar from 1.9% to 0.35% differing pixels. On a page from `spec --html`, `compare` prints that correction as a `css` line for the style's class. Check the box first: when the box is off, the cause is layout, not text.
- **Real brands:** a design of a real company's site is fine to implement in the user's own project; do not publish it as if it were the company's site.

## Working through the plugin

- An empty or null result, flagged by a `warning` under `resultAnalysis`, usually means a wrong id or name, not "nothing to do".
- `screenshot` caps the longest side at 1568 px, so a full page comes back scaled down. Screenshot sections, or use `render` for an exact full-size image.
- With more than one file open, commands without `--file` follow whichever file the user clicked last.
